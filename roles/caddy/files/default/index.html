OpenZFS on a single server

Checksums on every block, cheap snapshots and replication built in. These notes keep the decisions that are hard to change later and the commands used every month.

Pool layout

A pool is made of vdevs; data is striped across them, and redundancy lives inside each vdev. Losing any vdev loses the pool.

mirrorFast random IO, easy to grow in pairs, quick resilver. Good default for VMs and databases.
raidz2Survives two failed disks in the vdev. Best capacity for large media and backups; slower random IO.
specialMetadata and small blocks on SSD in front of an HDD pool. Must be mirrored — losing it loses the pool.
log / cacheSLOG only helps synchronous writes (NFS, databases). L2ARC rarely beats simply adding RAM.
zpool create -o ashift=12 tank \
  mirror /dev/disk/by-id/nvme-A /dev/disk/by-id/nvme-B \
  mirror /dev/disk/by-id/nvme-C /dev/disk/by-id/nvme-D
# ashift cannot be changed later: 12 = 4K sectors

Datasets and properties

Set common properties on the pool root so every dataset inherits them, then override per workload.

zfs set compression=lz4 atime=off xattr=sa tank
zfs create -o recordsize=16K tank/postgres     # match the DB page size
zfs create -o recordsize=1M  tank/media        # large sequential files
zfs create -o encryption=on -o keyformat=passphrase tank/private
  • lz4 is so cheap it usually makes IO faster; zstd trades CPU for a better ratio.
  • recordsize only affects newly written data.
  • Deduplication needs a lot of RAM per TB. Test with zdb -S before enabling it.

Snapshots and replication

A snapshot is instant and costs nothing until data diverges. Incremental send transfers only changed blocks, so off-site backups stay small.

zfs snapshot -r tank@2026-11-15
zfs list -t snapshot -o name,used,refer
zfs send -R -i tank@2026-11-08 tank@2026-11-15 | ssh backup zfs receive -Fu pool/tank
zfs rollback tank/postgres@2026-11-15            # back in time, instantly

Tools such as sanoid/syncoid automate rotation and replication on a schedule.

Maintenance

zpool status -x        # "all pools are healthy" or what is wrong
zpool scrub tank       # read and verify every block, monthly
zpool list -v          # capacity per vdev
arc_summary | head -40 # how well the ARC cache works
  • Keep pools below ~80% full; allocation gets slower as free space fragments.
  • Use /dev/disk/by-id paths, never /dev/sdX, which can change between boots.
  • Replace a failing disk with zpool replace and watch the resilver in zpool status.

OpenZFS 2.2+. RAID-Z expansion (adding a disk to an existing raidz vdev) arrived in 2.3.

OpenZFS на одном сервере

Контрольные суммы каждого блока, дешёвые снапшоты и встроенная репликация. Здесь — решения, которые потом трудно поменять, и команды на каждый месяц.

Устройство пула

Пул состоит из vdev; данные распределяются по ним, а избыточность живёт внутри каждого vdev. Потеря любого vdev — потеря всего пула.

mirrorБыстрый случайный ввод-вывод, легко расширять парами, быстрый ресильвер. Хороший выбор для ВМ и баз данных.
raidz2Переживает отказ двух дисков в vdev. Лучшая ёмкость для медиа и бэкапов; случайный ввод-вывод медленнее.
specialМетаданные и мелкие блоки на SSD перед пулом из HDD. Обязательно зеркалом — его потеря убивает пул.
log / cacheSLOG помогает только синхронной записи (NFS, базы). L2ARC редко выгоднее, чем просто добавить RAM.
zpool create -o ashift=12 tank \
  mirror /dev/disk/by-id/nvme-A /dev/disk/by-id/nvme-B \
  mirror /dev/disk/by-id/nvme-C /dev/disk/by-id/nvme-D
# ashift потом не изменить: 12 = сектора 4K

Датасеты и свойства

Общие свойства задайте на корне пула — их унаследуют все датасеты, — а затем переопределяйте под нагрузку.

zfs set compression=lz4 atime=off xattr=sa tank
zfs create -o recordsize=16K tank/postgres     # под размер страницы БД
zfs create -o recordsize=1M  tank/media        # большие последовательные файлы
zfs create -o encryption=on -o keyformat=passphrase tank/private
  • lz4 настолько дешёв, что обычно ускоряет ввод-вывод; zstd сжимает лучше ценой CPU.
  • recordsize влияет только на новые записанные данные.
  • Дедупликации нужно много RAM на каждый ТБ. Проверьте выгоду через zdb -S, прежде чем включать.

Снапшоты и репликация

Снапшот создаётся мгновенно и ничего не стоит, пока данные не начнут расходиться. Инкрементальная отправка передаёт только изменённые блоки, поэтому внешние бэкапы остаются маленькими.

zfs snapshot -r tank@2026-11-15
zfs list -t snapshot -o name,used,refer
zfs send -R -i tank@2026-11-08 tank@2026-11-15 | ssh backup zfs receive -Fu pool/tank
zfs rollback tank/postgres@2026-11-15            # назад во времени, мгновенно

Инструменты вроде sanoid/syncoid автоматизируют ротацию и репликацию по расписанию.

Обслуживание

zpool status -x        # «all pools are healthy» или что сломалось
zpool scrub tank       # прочитать и проверить каждый блок, раз в месяц
zpool list -v          # заполненность по vdev
arc_summary | head -40 # насколько хорошо работает кэш ARC
  • Держите пул заполненным не больше чем на ~80%: при фрагментации свободного места запись замедляется.
  • Используйте пути /dev/disk/by-id, а не /dev/sdX, которые могут меняться между загрузками.
  • Сбойный диск меняйте через zpool replace и следите за ресильвером в zpool status.

OpenZFS 2.2+. Расширение RAID-Z (добавление диска в существующий raidz vdev) появилось в 2.3.
